# Experiment Protocol

This document describes two things that currently coexist in this codebase:

1. The **original 3-session motor-only task** - still the live application
   served at `/`, driven by `app/frontend/js/experiment/legacyMotorOnlyController.js`.
2. The **Motor-Cognitive Dual-Task experiment engine** - implemented and
   tested (`app/frontend/js/experiment/experimentController.js`), but not
   yet wired into any screen. It runs today only via the test suite
   (`npm test`) and direct instantiation; the UI phase will connect it to
   real screens.

## 1. Original motor-only task (live)

Menu → general instructions → Session 1 instructions → 2-minute mouse
session → 90s break → Session 2 instructions → 2-minute mouse session →
90s break → Session 3 instructions → 2-minute mouse session → results →
save to Excel. Unchanged from the original UF_OPS application; see
`original/UF_OPS/` for the reference copy.

## 2. Motor-Cognitive Dual-Task experiment (engine only, not yet on screen)

### State machine

The controller has one idle state, `WELCOME`, before `start()` is called.
From there it walks an ordered sequence of phases, generated by
`app/frontend/js/experiment/phases.js#buildPhaseSequence(config)`:

```
WELCOME (idle)
  → INSTRUCTIONS
  → MOTOR_BASELINE
  → SUBTRACTION_3   → TRANSITION_3   → DUAL_TASK_3   → RECOVERY_3
  → SUBTRACTION_7   → TRANSITION_7   → DUAL_TASK_7   → RECOVERY_7
  → SUBTRACTION_17  → TRANSITION_17  → DUAL_TASK_17
  → COMPLETE
```

Note there is no `RECOVERY_17` - the experiment ends right after the final
dual-task block, matching the protocol diagram (no recovery is needed after
the last condition).

Phases with a `duration` advance automatically when their timer completes
(`app/frontend/js/timer/timer.js#Timer`). `INSTRUCTIONS` has no duration
and is only advanced by an explicit `controller.advance()` call - in the
current engine-only state that means a test or script; once the UI phase
exists, a "Begin" button will call it.

### Phase metadata

Every phase carries the following static metadata (see
`app/frontend/js/experiment/conditions.js`):

| Field | Meaning |
|---|---|
| `phaseType` | One of `instructions`, `motor`, `cognitive`, `transition`, `dual-task`, `recovery`, `complete` |
| `mouseActive` | Whether the mouse-accuracy task is running during this phase |
| `cognitiveActive` | Whether the participant is actively subtracting during this phase |
| `subtractionValue` | `3`, `7`, `17`, or `null` for phases with no subtraction condition |
| `duration` | Phase length in seconds, or `null` for phases advanced manually |

| Phase | phaseType | mouseActive | cognitiveActive | subtractionValue | duration (s) |
|---|---|---|---|---|---|
| INSTRUCTIONS | instructions | false | false | - | null |
| MOTOR_BASELINE | motor | true | false | null | 120 |
| SUBTRACTION_&lt;n&gt; | cognitive | false | true | 3 / 7 / 17 | 120 |
| TRANSITION_&lt;n&gt; | transition | false | false | - | 3 |
| DUAL_TASK_&lt;n&gt; | dual-task | true | true | 3 / 7 / 17 | 120 |
| RECOVERY_&lt;n&gt; (3 and 7 only) | recovery | false | false | - | 90 |
| COMPLETE | complete | false | false | - | null |

### Random starting numbers

`app/frontend/js/cognitive/randomNumber.js#generateStartingNumber` draws an
integer from `config.randomStartingNumberRange` (799-999). One number is
generated per subtraction condition, the first time `SUBTRACTION_<n>` is
entered, and is reused for that condition's `DUAL_TASK_<n>` phase rather
than generating a second number. Each condition's number is guaranteed to
differ from the immediately preceding condition's number.

### Configuration

All timing values above come from `config/experimentConfig.js` - nothing
in the controller, phases, or conditions modules hardcodes a duration or
the subtraction values. Changing the protocol's timing means editing that
one file.

### What is intentionally not implemented yet

- Any visual screens for the dual-task phases (next phase of work).
- Speech recognition or automatic subtraction-answer checking - the
  participant counts aloud; `cognitive/subtractionTask.js` only tracks
  which task is active, not whether it was answered correctly.
- A "stop mouse task early" capability - the existing mouse task always
  runs its full configured duration (see `mouse/mouseTask.js`); the
  controller's mouse integration interface documents this limitation
  rather than working around it.
